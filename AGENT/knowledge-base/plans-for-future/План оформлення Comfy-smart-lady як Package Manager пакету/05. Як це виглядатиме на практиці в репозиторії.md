Ось як це виглядатиме на практиці в репозиторії.

### 1. Що відбувається при `csl-agent send-feedback`

Команда робить таке:

1. Клонує центральний репозиторій у тимчасову папку (shallow clone).
2. Створює **нову гілку** з іменем:
   ```text
   feedback/20260829-141530
   ```
   (префікс `feedback/` + дата-час).
3. Копіює файли з `AGENT/feedback/overrides/` (і `local/`, якщо були) у відповідні місця канону всередині клону:
   ```text
   AGENT/feedback/overrides/agents/Comfy-smart-lady.md
           ↓
   AGENT/agents/Comfy-smart-lady.md   (у центральному репо)
   ```
4. Робить один коміт з повідомленням (те, що ти передав через `-m`).
5. Далі залежить від прапорців:

| Команда | Результат у репозиторії |
|---------|-------------------------|
| `csl-agent send-feedback` | Нічого не пушиться. Локально створюється патч-файл у проєкті. |
| `csl-agent send-feedback --push` | Гілка `feedback/YYYYMMDD-HHMMSS` з’являється на GitHub. |
| `csl-agent send-feedback --push --pr` | Гілка + одразу відкривається Pull Request. |

---

### 2. Як це виглядає на GitHub

**Список гілок:**
```text
main
develop
feedback/20260828-183012
feedback/20260829-091145
feedback/20260829-141530     ← нова
```

**Приклад Pull Request:**
```text
Title:   chore: feedback from project
Branch:  feedback/20260829-141530  →  main

Files changed:
  AGENT/agents/Comfy-smart-lady.md
  AGENT/scripts/anti_loop.py
  AGENT/knowledge-base/solutions/new-trick.md
```

Ти (або хтось) переглядаєш PR, приймаєш потрібні зміни, відхиляєш зайве, мержиш у `main`.

Після мержу:
- робиш новий реліз / підвищуєш версію пакета;
- у всіх проєктах виконуєш `csl-agent update` — і канонічні файли підтягуються.

### 3. Життєвий цикл гілки feedback

```text
[Проєкт A]                    [Центральний репо]
     │                                │
     │  overrides/зміни               │
     ▼                                │
collect-feedback                      │
     │                                │
     ▼                                │
send-feedback --push --pr  ──────────►│  створюється гілка
                                      │  feedback/20260829-141530
                                      │
                                      ▼
                                 Pull Request
                                      │
                          ┌───────────┴───────────┐
                          ▼                       ▼
                       Merge                   Close / Reject
                          │
                          ▼
                       main оновлено
                          │
                          ▼
                 новий реліз пакета (1.3.1)
                          │
                          ▼
              csl-agent update у проєктах
```

Гілки `feedback/*` після мержу можна спокійно видаляти (вони одноразові).

### 4. Важливі деталі поточної реалізації

- Кожна відправка = **окрема гілка** (не накопичує зміни в одній).
- Коміт один на всю пачку файлів з `feedback/`.
- Якщо файл у feedback є, а в каноні його ще не було — він з’явиться як новий.
- Якщо файл уже був — він просто перезаписується версією з overrides.
- Мета-файли (`*.meta.md`) у репозиторій **не потрапляють** — тільки самі змінені файли Агента.

---

### 5. Як можна покращити пізніше (за бажанням)

- Додати `--base main` / `--base develop`.
- Групувати feedback з кількох проєктів в одну гілку.
- Автоматично відкривати draft PR.
- Додавати в тіло PR список проєктів-джерел і коментарі з `.meta.md`.

Поки що реалізація навмисно проста і передбачувана: одна команда → одна гілка → один PR.

Хочеш щось змінити в іменуванні гілок, форматі коміту чи логіці копіювання файлів?
