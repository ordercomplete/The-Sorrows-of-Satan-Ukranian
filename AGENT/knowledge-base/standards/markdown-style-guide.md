# Стандарт форматування Markdown (Markdownlint та CommonMark)

**Дата фіксації:** 2026-09-28  
**Статус:** Обов'язковий канонічний стандарт проєкту  
**Офіційні джерела:**

- [CommonMark Specification v0.31.2](https://spec.commonmark.org/)
- [DavidAnson / markdownlint Rules Catalog](https://github.com/DavidAnson/markdownlint/blob/main/doc/Rules.md)
- Репозиторій правил у проєкті: `.markdownlint.json`, `.markdownlintignore`

---

## 1. Загальні принципи

1. **Передбачуваний рендеринг:** Кожен документ `.md` (включно з канонічними інструкціями, базою знань, документацією та журналами сесій і дій `memories_agent/`, `memories_{проєкт}/`) повинен строго відповідати цьому стандарту та коректно відображатися будь-яким парсером (GitHub, VS Code Preview, Continue, OpenCode, браузер).
2. **Контрольована строгість:** Лінтер ловить синтаксичні та структурні дефекти (відступи, незакриті блоки, зіпсовані таблиці), але не заважає вільному написанню системних промптів та інструкцій.
3. **Чистота кінців рядків і файлів:** Будь-який текстовий файл завершується рівно одним символом нового рядка (`\n`).

## 2. Основні правила форматування (з офіційного каталогу markdownlint)

### 2.1. Заголовки (Headings)

- **MD001 / heading-increment:** Рівні заголовків збільшуються лише на 1 за раз (після `#` має йти `##`, але не `###`).
- **MD018 / no-missing-space-atx:** Обов'язковий рівно один пробіл після символів `#` (наприклад, `## Розділ`, а не `##Розділ`).
- **MD019 / no-multiple-space-atx:** Не ставити більше одного пробілу після `#` (не `##   Розділ`).
- **MD022 / blanks-around-headings:** Заголовки повинні бути оточені порожніми рядками зверху і знизу.
  - *Виняток:* заголовок на самому початку файлу не потребує порожнього рядка зверху.
- **MD025 / single-title / single-h1:** Лише один заголовок 1-го рівня (`#`) на документ. Усі підрозділи починаються з `##` (H2) і нижче.
- **MD026 / no-trailing-punctuation:** Заголовки не повинні завершуватися крапкою, двокрапкою, комою або крапкою з комою (знаки `?` та `!` дозволені за сенсом).

### 2.2. Списки (Lists)

- **MD004 / ul-style:** Однаковий маркер невпорядкованих списків у межах документа (рекомендовано дефіс `-`).
- **MD005 / list-indent:** Вкладені списки повинні мати послідовний відступ (2 або 4 пробіли відповідно до рівня).
- **MD030 / list-marker-space:** Рівно один пробіл після маркера списку (`- пункт`, `1. пункт`).
- **MD031 / blanks-around-fences:** Код-блоки всередині списків або біля них мають відділятися порожніми рядками.
- **MD032 / blanks-around-lists:** Списки обов'язково відділяються порожнім рядком від попереднього та наступного абзацу чи таблиці.

### 2.3. Блоки коду (Code Blocks / Fences)

- **Синтаксична цілісність:** Кожен блок із трьома зворотними апострофами (```` ``` ````) зобов'язаний мати парний закриваючий блок на окремому рядку.
- **MD031 / blanks-around-fences:** Перед початком код-блоку та після його закриття обов'язковий порожній рядок.
- **MD040 / fenced-code-language:** Зазначення мови підсвічування (наприклад, ```` ```bash ````, ```` ```json ````, ```` ```powershell ````). Якщо тип даних довільний або фрагмент текстовий — дозволено plain text (правило MD040 вимкнено для шаблонів, але рекомендовано для коду).

### 2.4. Таблиці (Tables)

- **MD060 / table-column-count:** Кількість стовпчиків у заголовку, розділювачі (`|---|`) та рядках даних має суворо збігатися.
- **Розділювач заголовка:** Має містити щонайменше 3 дефіси на комірку (`| --- | --- |`).
- **Відступи біля таблиці:** Таблиця обов'язково відокремлюється порожніми рядками зверху та знизу, інакше парсер трактує її як продовження попереднього списку або абзацу (найчастіша причина помилок `MD032` та `MD055`/`MD056`).

### 2.5. Пробіли та розриви рядків (Whitespace)

- **MD009 / no-trailing-spaces:** Заборонено випадкові пробіли наприкінці рядків.
  - *Конфігурація проєкту:* параметр `"br_spaces": 2` дозволяє рівно 2 пробіли в кінці рядка, якщо потрібен явний перенос рядка (`<br>`) без створення нового абзацу.
- **MD012 / no-multiple-blanks:** Заборонено більше 1 послідовного порожнього рядка (`maximum: 1`).
- **MD047 / single-trailing-newline:** Файл обов'язково має закінчуватися рівно одним переводом рядка. Жодних порожніх «хвостів» або обривів без LF/CRLF.

## 3. Особливості конфігурації проєкту (`.markdownlint.json`)

У нашому репозиторії налаштовано файл `.markdownlint.json`, який оптимізовано під специфіку системних агентів та AI-асистентів:

| Правило | Стан у проєкті | Обґрунтування |
| :--- | :--- | :--- |
| **MD013** (line-length) | **Вимкнено** | Промпти, технічні вимоги та регулярні вирази формулюються цілісними довгими рядками, примусовий розрив на 80 символів ламає читабельність. |
| **MD033** (no-inline-html) | **Вимкнено** | Необхідно для системних HTML-коментарів ініціалізації: `<!-- 🔴 INIT-GATE: ... -->`, які читаються системними парсерами агентів. |
| **MD041** (first-line-heading) | **Вимкнено** | У стабах першими рядками є службові коментарі гейту, а сам H1 іде після них. |
| **MD034** (no-bare-urls) | **Вимкнено** | Дозволяє писати прямі посилання у технічних логах без обов'язкового обгортання в `<url>`. |
| **MD024** (no-duplicate-heading) | **siblings_only: true** | Дозволяє однакові назви підрозділів (наприклад, `## Огляд`, `## Приклад`) у різних батьківських секціях. |

## 4. Корисні команди для розробника

Швидка перевірка форматування через CLI:

```powershell
# Перевірити все ядро Агента
npx --yes markdownlint-cli --config .markdownlint.json "AGENT/agents/*.md" "AGENT/skills/**/SKILL.md"

# Автоматично виправити прості дефекти (порожні рядки, пробіли, кінці файлів)
npx --yes markdownlint-cli --config .markdownlint.json --fix "AGENT/**/*.md"
```
