## 1. Базові принципи версіонування

1. **Атомарність комітів:** Один коміт вирішує рівно одну логічну задачу або містить один пов'язаний набір змін (не змішувати рефакторинг, виправлення помилок та оновлення залежностей).
2. **Чистота робочого дерева (`Working Tree`):** Перед виконанням перемикання гілок, оновлення (`pull`) або коміту завжди перевіряти стан через `git status`.
3. **Захист головної гілки (`main`):** Робочий код у `main` завжди має бути в працездатному та перевіреному стані (тести проходять, лінтер не видає помилок ядра).
4. **Ідемпотентність і чистота артефактів:** Тимчасові файли, кеші середовищ (`.tmp`, `node_modules`, `__pycache__`) та локальні логи ніколи не повинні потрапляти під версійний контроль (налаштовується через `.gitignore`).

## 2. Стандарт оформлення повідомлень комітів (Conventional Commits)

Формат повідомлення коміту:

```text
<тип>(<область>): <короткий опис у наказовому способі>

[необов'язкове детальне тіло пояснення]

[необов'язковий підвал з посиланням на задачі/PR]
```

### 2.1. Основні типи (Types)

- `feat`: Нова функціональність для користувача або Агента.
- `fix`: Виправлення дефекту або помилки у коді/шаблонах.
- `docs`: Зміни виключно в документації чи коментарях.
- `style`: Правки форматування, пробілів, відступів, які не змінюють поведінку коду (наприклад, виконання вимог `markdownlint`).
- `refactor`: Переробка коду без додавання нових функцій і без виправлення багів.
- `test`: Додавання нових або виправлення існуючих тестів.
- `chore`: Зміни в процесі збірки, скриптах синхронізації або допоміжних інструментах (без впливу на продакшн-код).

### 2.2. Приклади правильних комітів

- `style(markdown): format core agent documentation to comply with markdownlint`
- `fix(sync): append trailing newline on stub file generation`
- `feat(config): add markdownlint configurations to distribution manifest`
- `docs(kb): add markdown and git reference guidelines`

## 3. Основні команди Git та сценарії використання

### 3.1. Перевірка стану та порівняння змін

```bash
# Перевірити статус робочого дерева (короткий вигляд)
git status -s

# Переглянути зміни без виклику пейджера (зручно в терміналах агентів)
git --no-pager diff

# Переглянути лише назви та статус змінених файлів
git --no-pager diff --name-status

# Переглянути список підготовлених (staged) змін
git --no-pager diff --staged
```

### 3.2. Додавання та фіксація змін

```bash
# Додати конкретні файли до індексу
git add path/to/file.ext

# Додати всі змінені файли поточного каталогу
git add .

# Створити коміт з чітким повідомленням
git commit -m "feat(module): add descriptive summary"
```

### 3.3. Робота з віддаленим репозиторієм (Remote)

```bash
# Отримати останні зміни з сервера без автоматичного злиття
git fetch origin

# Підтягнути та злити зміни поточної гілки
git pull origin main

# Відправити локальні коміти на віддалений сервер
git push origin main
```

### 3.4. Скасування дій та відновлення

```bash
# Відновити змінений файл робочого дерева до стану з останнього коміту
git restore path/to/file.ext

# Прибрати файл з індексу (unstage), зберігши зміни на диску
git restore --staged path/to/file.ext

# Перевірити, чому файл ігнорується або не ігнорується
git check-ignore -v path/to/file.ext
```

## 4. Специфіка роботи з Git у системі Comfy-smart-lady

1. **Синхронізація стабів і маніфесту:** Будь-які зміни в `AGENT/` перед комітом потребують перевірки актуальності `agent_config/manifest.json` та `agent-lock.json`.
2. **Бекапи та логи:** Папки `agent_config/backup-chat/` та `AGENT/memories_agent/` є локальними робочими артефактами й захищені відповідними правилами ігнорування.
3. **Автономність агентів:** Під час виконання команд через агентський термінал заборонено використовувати інтерактивні команди, що блокують вивід (завжди використовувати прапорець `--no-pager`).
