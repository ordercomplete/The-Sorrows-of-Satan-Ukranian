## Завантаження знань (між сесіями навіть впродовж тієї ж доби) для пошуку покращень роботи агента

При кожній новій сесії обов'язково завантажуй:

- `AGENT/knowledge-base/README.md` — структура бази знань, як користуватись.
- `AGENT/knowledge-base/code-patterns/*.md` — патерни коду ComfyUI.
- `AGENT/knowledge-base/solutions/*.md` — знайдені рішення проблем.
- `AGENT/knowledge-base/external-resources/*.md` — корисні посилання з поясненням.

База знань допомагає не шукати одне й те саме двічі, особливо для локальних моделей 30-40B.

## Анти-цикл механізм (критично!)

### Детектування циклів

1. **3+ однакові tool call'и поспіль** — якщо результат той самий, негайно зупинитися і зробити висновок.
2. **Перевірка результату** — після кожного tool call аналізувати, чи змінився результат порівняно з попереднім викликом.
3. **Порожній результат або помилка** — зроби висновок і зміни напрямок роботи.

### Анти-цикл фраз

1. Не повторювати одну й ту саму думку в кількох відповідях поспіль.
2. Максимум 2 однакові фрази — потім зміни формулювання або йди далі.
3. Якщо зациклилась на фразі "Перевірю..." / "LoRA Manager використовує..." — напиши що саме робитимеш далі і роби.

### Журнал циклів та зупинок

Після відновлення якщо була не передбачувана зупинка проаналізуй причину, запиши в `memories/errors/error-log.md`:

- Причина, наслідки, рекомендації
Критичні цикли фіксувати в `memories/errors/error-log.md` - запуск команди: "шаблон отримання поточного часу":
- Дата, тривалість, кількість ітерацій
- Причина, наслідки, рекомендації

## Очищення контексту (критично!)

### Рівні заповнення контексту

| Заповнення | Дія | Час до початку дії |
| ------------ | ----- | ------------------- |
| **0–50%** — легкий | Звичайна робота, без додаткових дій | — |
| **50–70%** — середній | Фіксувати прогрес у файли тільки при завершенні підзадач (не кожен крок!) | При досягненні 50% |
| **70–80%** — важкий | Оновити `memories/session/` з поточним статусом, підготувати резюме | При досягненні 70% |
| **80–90%** — критичний | Завершити поточну дію → записати повне резюме → запропонувати новий чат | Одразу при досягненні 80% |
| **90%+** — переповнений | Зупинити все → записати резюме → закрити чат з пропозицією продовжити в новому | Миттєво |

> **Важливо:** Для локальних моделей 30-40B таймаут відбувається на ~65-75% через те що модель не встигає згенерувати відповідь до таймауту (60-120 сек). Тому починати очищення при 70%.

### Коли оновлювати файли прогресу (обов'язково!)

- **Тільки при завершенні підзадачі** — не кожен крок, а тільки результат
- **При досягненні 50% заповнення** — перший фікс прогресу
- **При зміні напрямку роботи** — записати що змінилось
- **При помилці** — записати причину та рішення

### Формат резюме для нового чату

```markdown
# Статус сесії — YYYY-MM-DD HH:MM

## Що зроблено
- ✅ Дія 1
- ✅ Дія 2

## Поточний статус
- 🔥 Робота над: [опис]
- 📍 Останній крок: [що саме робили]

## Наступні кроки
1. Крок 1
2. Крок 2

## Важливі нотатки
- Контекст: [заповнення %]
- Проблеми: [якщо є]
```

## Оптимізація для локальних моделей 30-40B (критично!)

Читай `memories/errors` та запроваджуй для покращення роботи агента.

### Проблема

Таймаут "Sorry, no response was returned." відбувається в більшості випадків на ~65-75% заповнення контексту через те що модель не встигає згенерувати відповідь до таймауту (60-120 сек).

### Рішення

1. **Більше tool call'ів поспіль** — максимум 5-6 перед висновком (збільшено з 3-4).
2. **Коротші відповіді** — без зайвих деталей, тільки факти.
3. **Не читати великі файли повністю** — використовувати grep/search замість read_file для пошуку.
4. **Об'єднувати дії** — використовувати multi_replace_string_in_file замість окремих редагувань.
5. **Не дублювати контекст** — не повторювати в відповіді те що вже є в історії чату.
6. **Фіксувати прогрес тільки при завершенні підзадач** — не кожен крок, а тільки результат.

### Приклади оптимізації

❌ **Погано:** `list_dir` → `list_dir` → `list_dir` → аналіз (3 однакові tool call'и без результату)
✅ **Хорошо:** `list_dir` → аналіз → `grep` для пошуку → висновок (з результатами)

❌ **Погано:** Детальний опис кожного кроку в відповіді
✅ **Хорошо:** Короткий висновок + посилання на файл журналу

### Як робити більший об'єм роботи без зупинки

1. **Групувати пов'язані дії** — замість `list_dir` → `read_file` → `grep`, робити `grep` → одразу редагування.
2. **Не оновлювати файли кожен крок** — тільки при завершенні підзадачі або зміні напрямку.
3. **Уникати послідовних `list_dir`** — якщо перший повернув структуру, не перевіряти знову.
4. **Використовувати grep замість read_file** — для пошуку в великих файлах.
5. **Об'єднувати редагування** — multi_replace_string_in_file замість 3-4 окремих replace.
6. **Не пояснювати очевидне** — якщо файл відомий, не читати його знову.
